# AI 分析设计

## 先解决什么问题

Cycle 已能计算功率、心率、分段、最佳努力和训练负荷。AI 最有价值的工作，是把这些已算好的信息联系起来，帮助用户理解“这次训练执行得怎样，下一次具体改什么”。计算仍由本机分析模块完成，模型负责解释与建议。

首版采用 **单次活动复盘**，入口放在活动详情。它不需要另建一个空白聊天页面，也不会要求用户先想出一个问题。用户可以直接复盘，也可以补充“重点看最后两组间歇”“这次是否适合恢复骑”等关注点。

一份有用的复盘应回答：

1. **训练特征**：这次更接近耐力、节奏、阈值、短间歇还是混合训练？依据哪些实际指标？
2. **执行质量**：功率是否稳定，间歇是否衰减，心率与功率的变化是否一致？
3. **关键片段**：最值得回看的是哪组区间、哪个持续时间的最佳努力？
4. **下一次建议**：给出少量可执行的调整，例如保持目标功率、减少组数或延长恢复，并解释依据。

强度结论依据活动当天的 FTP。模型不因一次非全力活动而降低用户 FTP，也不自动修改 FTP 或训练计划；实际刷新纪录的提示继续由已有确定性规则产生。

## 功能优先级

| 功能 | 价值 | 数据条件 | 建议阶段 |
| --- | --- | --- | --- |
| 单次活动复盘 | 将本次指标与区间连接成可操作的结论 | 一次已完成活动 | 首版 |
| 计划与实际对照 | 解释“哪里完成、哪里偏离、下一次如何调整” | 结构化训练与已关联实际活动 | 下一阶段 |
| 相似活动对比 | 判断同类骑行的稳定性、效率与进步 | 用户明确选择的两次活动 | 下一阶段 |
| 训练周回顾 | 结合训练分布解释本周执行和下周重点 | 用户选择的时间范围与计划 | 后续 |
| 自然语言生成训练草案 | 把目标转成可预览的训练结构 | 用户目标、时长、FTP 与可训练时间 | 后续，先预览再保存 |
| 恢复与健康趋势解释 | 联系睡眠、静息心率等变化 | 单独选择并明确授权发送的健康指标 | 独立设计后接入 |

首版不做持续悬浮聊天框、自动生成大量日报、自动改动记录或“万能 AI 教练”。这些形式容易增加操作和信息噪声，难以验证它们是否帮助用户完成训练。

## 首版交互

设置中保存 API 地址和本机密钥，连接后读取 `/models`。列表不替用户选择模型；选中后点击“保存模型”。可以更换服务地址、更新密钥或移除连接。

活动详情点击“AI 复盘”，可看到本机保存的问答、发送目的地、当前模型及可展开的训练摘要。点击发送后才调用模型。追问携带同一 API 地址下最近六轮问答的有限上下文；更换地址后，旧记录仍可查看。活动摘要、模型或会话版本变化后，需要重新打开复盘。

每项活动可保存至多 200 轮问答。清空对话或删除活动会移除对应记录。训练 JSON 备份不含复盘问答；从备份替换训练库时会清除当前复盘记录。

输出作为活动分析旁的解释文本，不覆盖本机计算。结果在本次应用会话内按活动暂存，关闭再打开可以继续查看；不自动加入活动备注或备份。

## 数据范围

发送的是服务器按白名单生成的摘要：运动类型、时长、距离、速度、功率、心率与踏频的汇总、NP/IF/TSS、FTP 基准、采样覆盖、最佳努力、区间及分布。缺测保留为空，不由模型补造记录。

首版不发送活动名称、日期、个人姓名、用户备注、GPS 坐标、地图路线、设备标识、原始 FIT/XML、逐秒采样或 Apple 健康记录。用户填写的关注问题会一同发送，可以在点击生成前核对。天气、历史多活动和健康数据不因开启 AI 连接而被自动读取或发送。

密钥放在数据目录的独立本机配置文件，接口状态只返回“是否已保存”，不回显密钥；训练 JSON 备份与源码发布均不包含密钥。读取模型列表仅请求模型目录，不携带活动数据。

## 如何评价效果

优先检查复盘是否引用本次真实数据、是否区分事实和推测、是否指出值得回看的区间，以及建议是否具体。不同模型用同一份已确认摘要比较；不以报告长度或语气肯定程度评价优劣。基础指标与 FTP 更新仍可用现有测试独立验证。
